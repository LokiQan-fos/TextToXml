## 2. Findings

### 2.1 Cross-story pattern: the mapping annex has no scale/precision field — this is *why* the decimal-scale defect hit 5 mappers independently

**Source:** `_bmad-output/implementation-artifacts/annexe-mapping-dispatch-epic4.md:37` (and every other table header in the file, lines 95/186/200/213/232/258/275/285/313) — the annex's only columns are `| Colonne | Statut | Source / Règle |`. Example row, line 51: `| DiametreProduit | sourcée | KAPE22.DiametreProduit |`. Cross-referenced against `deferred-work.md` §"Deferred from: story-4.6 implementation (2026-09-16)" and §"Deferred from: code review of story-4.3 (2026-09-15)", which record the same defect independently discovered in `OrdreFabricationMapper` (Story 4.3, 2026-09-15) and then in four more mappers (`SectionChargeLingotMapper`, `SectionChargeChutageMapper`, `SectionChargeDecoupeMapper`, `SectionChargePitsMapper` — Story 4.4's own mappers, escalated during Story 4.6, 2026-09-16).

**Disposition:** already tracked as a fix-now item (`story-4-6-decimal-scale-defect-story-4-3-bis`, open in `sprint-status.yaml`) — not re-added here. What *is* new at the retro level is the root cause: Story 4.2's annex format (AC-FR17-1) records a column's *source field*, never its *scale or unit*. A column marked `sourcée` reads as "no further rule needed," so five independent per-column-reviewed mappers (4.3's own review on 2026-09-15, then 4.4's downstream review escalating on 2026-09-16) all inherited the same gap without any of those five reviews being wrong on its own terms — the annex itself has no place to record "this KAPE22 int needs a decimal rescale." This is a spec-to-implementation reconciliation finding: the Story 4.2 annex format, not any one mapper, is the structural blind spot.

**Process lesson → action item A-1** (below): extend the annex format with an explicit scale/precision field for any `sourcée` column whose target CLR type is `decimal` and source is `int`/`int?`, and add a completeness-test branch (extending `AC-FR17-5`'s existing family) that fails when a `decimal` target column's annex row omits it. This is exactly the kind of "AC completeness gate" pattern Epic 3's retro praised for `AcCoverageCompletenessTests` (SM-1) — the same idea applied to the mapping annex.

### 2.3 Diff-scope review (bmad-review, cross-story seam)

`bmad-review` was invoked with the adversarial, edge-case-hunter, and verification-gap lenses, scoped to the Story 4.3/4.4 → 4.5 → 4.6 composition (`Kape22ImportBundleMapper.cs`, `Kape22ImportBundle.cs`, `Kape22Persister.cs`, `Kape22FichierProcessor.cs`, and the mapper files they compose), explicitly excluding what each story's own `/run-review` pass already covers.

**Verification-gap lens finding — Unit-tier tests never assert the 9 downstream tables on a successful import:**

**Source:** `tests/Kape22Importer.Tests/Kape22FichierProcessorTests.cs:91-107` and `:188-201` (`Import_CleanFichier_RunsThroughToTheInsert_AcFr13_1`, `Import_Success_ResultShape_AcFr13_5`), composing `src/Kape22Importer/Kape22FichierProcessor.cs:71-93` → `Kape22ImportBundleMapper.cs` → `src/Kape22Importer/Persistence/Kape22Persister.cs:111-131`.

**Trigger condition:** any regression in the `Kape22FichierProcessor` → `Kape22ImportBundleMapper` → `Kape22Persister` composition that drops one or more of the 9 downstream table inserts on a successful import (e.g. `Kape22Persister.PersistMapped` stops calling one of the `AddIfPresent(...)` lines, or stops adding `OrdreFabricationRows`/`CouleeRows`/`ConsignesRows`, `Kape22Persister.cs:113-126`) — as long as `L_D_KAPE22` and the `OK` `L_D_LOG_COMMANDE` row still insert.

**Evidence:** `Kape22FichierProcessorTests.cs` is `[Trait("Category", TestCategory.Unit)]` (runs everywhere, no SQL Server needed, via `InMemoryContextFactory`/`UseInMemoryDatabase()` — `TestSupport.cs:225-242`) and its only `Import()`-success assertions touching `AscoLsiDbContext` are `Kape22Rows` and `LogCommandeRows`; no `SectionCharge*`/`OrdreFabrication`/`Coulee`/`Consignes` assertion appears anywhere in the file, despite the in-memory context supporting one with zero extra setup. A grep of the whole test project for the 9 downstream `DbSet` names finds them in exactly 4 files — `RejectionAtomicityIntegrationTests.cs`, `EndToEndImportIntegrationTests.cs`, `TransactionalPersistenceTests.cs`, `PersistenceSmokeTests.cs` — and all of those are `[Trait("Category", TestCategory.Integration)]` classes built of `[SkippableFact]` methods that skip cleanly when no local SQL Server instance is reachable (this repo has no Docker/Testcontainers harness, per project-profile.md's "Stratégie d'intégration").

**Potential consequence:** the `Category=Unit` suite — the only layer guaranteed to run on every machine and in CI without a provisioned SQL Server instance — would stay fully green even if the FichierProcessor/BundleMapper/Persister composition silently stopped writing 9 of the 10 AscoLSI dispatch tables on every successful import. Only the `SkippableFact` integration tests would catch it, and those are designed to skip cleanly rather than fail when the environment lacks SQL Server.

**Disposition:** fix now — cheap and high-value: extend the existing in-memory `Kape22FichierProcessorTests.cs` success assertions to also read back the 9 downstream `DbSet`s (the in-memory context already supports it, no new fixture needed). Routed as action item A-2 below.

**Adversarial lens finding — the same untrimmed-field pattern hits `OF`, more broadly than Coulee: `Kape22Mapper` trims `OF` only for its own `MapResult.OF`, never on `entity.OF` itself, so every Epic 4 mapper inherits the untrimmed value:**

**Source:** `src/Kape22Importer/Kape22Mapper.cs:78-92` (the reflective per-Champ copy loop that sets `entity.OF` — confirmed by reading the file: no `.Trim()` anywhere in the loop) versus `Kape22Mapper.cs:137` (`string of = file.Message.OF.Trim();` — feeds only the returned `MapResult.OF`/`bundle.OF`, a separate local variable, never written back onto `entity`). Every Epic 4 mapper reading `source.OF` (`OrdreFabricationMapper.cs`, all 7 `SectionCharge*Mapper.cs`, `ConsignesMapper.cs`) therefore reads the untrimmed `entity.OF`, while `Kape22Persister` uses the already-trimmed `bundle.OF` for `L_D_LOG_COMMANDE.OF` and the D22 anti-duplicate guard.

**Potential consequence:** if a real `L_D_KAPE22.OF` Champ carries padding (plausible for a fixed-width field — this is exactly why line 137 trims its own copy), `L_D_LOG_COMMANDE.OF` (trimmed) and `L_D_ORDRE_FABRICATION.OF`/`L_D_CONSIGNES.OF`/every `L_D_SECTIONCHARGE_*.OF` (untrimmed) can hold visibly different spellings of the same business key for the same import — breaking `AD-7`'s implicit expectation that a scalar FK is written identically everywhere it appears, and silently missing rows for any operator query or downstream legacy screen that joins on exact `OF` equality.

**Why this is a retro-level (not story-level) finding:** the untrimmed `entity.OF`/`entity.Coulee` pattern is pre-existing Epic 2 code (`Kape22Mapper.cs` was not touched by any Epic 4 commit — absent from the `git_evidence.py` file list for this range) — Epic 2 never fanned these fields out beyond `L_D_KAPE22` itself, so the gap was latent and harmless. Epic 4 is what turns it live, by copying `entity.OF`/`entity.Coulee` verbatim into 9 more tables' scalar key columns (`AD-7`) with no central place performing the trim. No single Epic 4 story's own review would have looked back into Epic 2's `Kape22Mapper` to catch this — it is exactly the kind of seam a full-epic retrospective is for.

**Disposition:** fix now, at the root cause rather than at each of the 9 downstream mappers — trim `entity.OF` and `entity.Coulee` once, inside `Kape22Mapper.Map`'s existing per-Champ loop (or immediately after it), so every current and future consumer inherits clean values instead of each remembering to trim at its own read site (the way `Kape22Persister` already does defensively, inconsistently, at three separate call sites). Consolidated with the Coulee-specific instance of the same pattern (edge-case lens finding below) into a single action item, A-3.

**Edge-case lens finding — `CouleeMapper` never trims `IdCoulee`, but the persister's reuse check trims before comparing (same pattern, confirmed independently by two lenses):**

**Source:** `src/Kape22Importer/CouleeMapper.cs:41` (`IdCoulee = source.Coulee` — no `.Trim()`, confirmed by reading the file: no trimming anywhere in the mapper) versus `src/Kape22Importer/Persistence/Kape22Persister.cs:89-90` (`string coulee = entity.Coulee.Trim(); bool couleeAlreadyExists = context.CouleeRows.Any(row => row.IdCoulee == coulee);`) and `:116` (`context.CouleeRows.Add(bundle.Coulee!)` — the untrimmed value, when not already present).

**Trigger condition:** a `L_D_KAPE22.Coulee` value carrying leading/trailing whitespace (plausible for a fixed-width legacy text field — `Kape22Persister.cs` itself defensively `.Trim()`s `entity.Coulee` and `bundle.OF` at every read site, implying the pipeline does not guarantee these fields arrive pre-trimmed).

**Potential consequence:** the first Fichier naming a padded Coulee number stores an **untrimmed** `IdCoulee` in `L_D_COULEE` (the `CouleeMapper` never trims it). A later Fichier for the same cast, whose raw `Coulee` carries the same padding, computes `coulee = entity.Coulee.Trim()` and compares it against the stored untrimmed value — the comparison never matches, `couleeAlreadyExists` comes back `false`, and the persister tries to insert the same `IdCoulee` again, causing a PK-violation `PersistenceError` on an otherwise valid, already-known Coulee (the exact "several OF share one cast" scenario `AD-1`'s bundle design and the Spec Change Log 2026-09-16 reuse logic exist specifically to handle without error).

**Disposition:** fix now — trim `IdCoulee` in `CouleeMapper.Map` (`source.Coulee.Trim()`), matching the trim already applied at every other Coulee read site in `Kape22Persister`. Routed as action item A-3 below.

**Edge-case lens finding — an FR-20 rejection message embeds the untrimmed `OF`, while the stored log row uses the trimmed one (minor, diagnostic-only):**

**Source:** `src/Kape22Importer/Kape22ImportBundleMapper.cs` (e.g. `Message = $"OF '{kape22.OF}' : ..."` in `AddIngotFurnaceDistributionViolation`/`AddHotCouleeFormatViolation`/`AddMissingEnfournementInstructionViolation`, all reading `kape22.OF` directly) versus `Kape22Persister.cs:161` (`BuildLogRow(bundle.OF.Trim(), message)`) — the same defensive-trim pattern noted above.

**Potential consequence:** if `L_D_KAPE22.OF` carries padding, the `L_D_LOG_COMMANDE.OF` column (trimmed) would diverge cosmetically from the `OF '<value>'` text quoted inside that same row's `Message`, and from the value written to `*.errors.json`. Diagnostic-only — `OF` is used here as free text inside a message, never as a comparison key, so no functional impact (unlike the Coulee case above).

**Disposition:** accept as-is / low-priority cosmetic — not routed as a separate action item; worth folding into A-3's fix if that PR touches these message-construction sites anyway, but not worth its own story.

**Edge-case lens finding — the FR-20-2 ingot/furnace distribution control is silently skipped whenever Refroidissoirs is "not applicable," with no independent check that this is legitimate:**

**Source:** `Kape22ImportBundleMapper.cs:84-87` (`if (refroidissoirs is null) { return; }`) — `Refroidissoirs`'s own applicability rule (`SectionChargeApplicability.IsApplicable`, `SectionChargeRefroidissoirsMapper.cs:15-18`) is a presence check on `CodeOpeRefroidissoir`/`RangOpeRefroidissoir` alone, with no relationship to `NombreDemiProduit`.

**Potential consequence:** if legacy KAPE22 data can have a nonzero `NombreDemiProduit` on an OF whose `CodeOpeRefroidissoir`/`RangOpeRefroidissoir` are empty (data-entry gap rather than a genuinely Refroidissoirs-less OF), `AC-FR20-2`'s distribution control never runs for that Fichier — it passes silently rather than being flagged. `AC-FR20-2`'s own Given clause ("*Given* a mapped `L_D_SECTIONCHARGE_REFROIDISSOIRS`...") only defines behavior when Refroidissoirs *is* mapped, so this is not a violation of the letter of the AC, but the AC is silent on whether that combination (Refroidissoirs inapplicable, `NombreDemiProduit` nonzero) can occur in real data.

**Disposition:** open question — routed to §7 (Open Questions) rather than a fix-now action item, since resolving it needs a legacy-data read (does `CodeOpeRefroidissoir`/`RangOpeRefroidissoir` ever go empty on an OF with real demi-produits?), the same "assumed, unverified" pattern already governing several annex columns in this epic — not a code decision.

**Adversarial lens finding — the hot/cold Coulee marker (`CodeConsignePits == "1"`) is hard-coded independently in two collaborators:**

**Source:** `Kape22ImportBundleMapper.cs:113` (`bool isHot = kape22.CodeConsignePits != "1";`, inline literal) versus `Kape22Persister.cs:36,91` (`private const string ColdConsignePits = "1";` ... `if (entity.CodeConsignePits == ColdConsignePits && ...)`).

**Potential consequence:** `AC-FR20-3`'s hot-Coulee-format check and `AC-FR20-5`'s cold-Coulee-existence check each own a separate copy of the same business marker. An edit to one without the other (e.g. a future business-rule change to the marker value) silently makes the two collaborators disagree on which Coulees are cold, with no compiler or test signal tying them together.

**Disposition:** fix now — extract one shared constant (e.g. on `Kape22ImportBundle` or a small shared type both already reference) rather than two independent literals. Cheap; routed as action item A-4 below.

**Adversarial lens finding — a `SectionCharge*` CodeOperation collision inside one bundle would raise an uncaught `InvalidOperationException`, not a `PersistenceError`:**

**Source:** `Kape22Persister.cs:126` (`context.ConsignesRows.AddRange(bundle.Consignes);`) inside the same `try` block whose `catch` only matches `DbUpdateException or DbException` (`Kape22Persister.cs:139-142`), versus `ConsignesMapper.cs:82-88`'s own comment, which already documents the precondition this relies on: `L_D_CONSIGNES`'s natural key `(OF, CodeOperation, TypeConsigne, ConsigneGPAO)` stays unique across the 7 sections of one OF "as long as their `CodeOperation` values differ, which every reference Fichier read so far satisfies" — i.e. the collision risk itself is already a known, accepted, unconfirmed assumption (`deferred-work.md` § "story-4.4 mapper implementation"), not a new finding.

**What is new:** EF Core's change tracker throws a client-side `InvalidOperationException` ("another instance with the same key value is already being tracked") at `Add`/`AddRange` time itself when two entities in the same batch share a key — before `SaveChanges` ever runs, and before any SQL executes. `Kape22Persister`'s exception filter (`when (exception is DbUpdateException or DbException)`) does not match `InvalidOperationException`, so if the already-known `CodeOperation`-collision risk is ever actually hit by a real Fichier, the exception escapes `Persist`/`Import` entirely uncaught. It is then only caught by `InboxScanner`'s generic per-Fichier `try/catch` (Story 3.2 decision D2), which quarantines the Fichier to `error/` with no `ConversionError` and no `L_D_LOG_COMMANDE` REJETÉ row — silently missing `AD-4`'s "every failure becomes an identified, journalized cause" invariant for exactly this one failure mode, even though every *other* SQL-level failure is already covered.

**Disposition:** fix now — widen `Kape22Persister`'s exception filter to also catch `InvalidOperationException` from this specific EF Core client-side path (or pre-check `bundle.Consignes` for a duplicate natural key before `AddRange`, surfacing it as a proper `ConversionError` instead of an exception). This closes a real gap in an already-acknowledged risk rather than opening a new one. Routed as action item A-5 below.

**Considered and not routed — the FR-20 controls vs. the persister's cold-Coulee check run in two separate passes, so a Fichier failing both only reports one cause per submission:**

Both the edge-case and adversarial lenses independently flagged that `Kape22Persister.Persist` (`Kape22Persister.cs:59-61`) only reaches the cold-Coulee existence check (`AC-FR20-5`) when `bundle.Success` is already `true` — a bundle that already fails one of `Kape22ImportBundleMapper`'s three pure `FR-20` checks is routed to `PersistRejected` instead, so the cold-Coulee cause (which requires a DB read) is never evaluated in the same submission. **Verified against the spec and found to be by design, not a defect:** `epics.md`'s own `AC-FR20-5` Given clause is explicit — "*Given* un bundle **qui franchit le garde-fou** et dont la coulée est «froide»" ("*given* a bundle that **already crosses the guard**") — the cold-Coulee check is scoped from the start to only run on a bundle that already passed the pure checks, precisely because it is the one `FR-20` control that needs a DB read and could not live inside the pure `Kape22ImportBundleMapper` (`epics.md`: "AC-FR20-5 — contrôle métier FR-20, exécuté ici pour la lecture base qu'il requiert, AD-1"). Recorded here for traceability — a reader should be able to tell this was checked and dismissed, not missed.

### 2.4 Lower-priority findings — accepted, not routed to a fix-now action item

- **Independent clock reads for one import event** (`OrdreFabricationMapper.cs:25-26`, `CouleeMapper.cs:20-21`, `Kape22Persister.cs:194`): each calls `(timeProvider ?? TimeProvider.System).GetUtcNow()` at its own site rather than the orchestrator sampling one timestamp and threading it through the bundle. In production this can leave `L_D_ORDRE_FABRICATION`/`L_D_COULEE`/`L_D_LOG_COMMANDE` timestamps for the same atomic import a few milliseconds apart — invisible under tests, which inject one `FixedClock` instance. Same family as the Epic 3 `ParisTimeZone`-duplicated-four-ways hygiene fix, but for clock *reads* rather than `TimeZoneInfo` *instances*. Minor audit-trail cosmetic; accepted, not worth its own story.
- **`Kape22Persister`'s `AddIfPresent` null-guard for `SectionChargePits` is now dead code**: `AC-FR20-4` makes a `null` `SectionChargePits` an unconditional bundle-level rejection (`Kape22ImportBundleMapper.cs:128-145`), so any bundle that actually reaches `PersistMapped` always has a non-null `SectionChargePits` — the generic `AddIfPresent` null-check applied to it (`Kape22Persister.cs:122`) can never see `null` in practice, unlike the other 6 truly-optional sections it is also used for. Harmless (using the shared helper for all 7 is simpler than special-casing Pits), but the never-null invariant is asserted nowhere — a latent trap if a future edit to Pits' applicability rule assumes the persister's null-check is still meaningful. Accepted; worth a one-line comment at most, not an action item.
- **`OF` value inside an FR-20 rejection message vs. the log row's own `OF` column**: both lenses independently converged on this (§2.3 edge-case finding) — cosmetic-only, superseded by the broader OF-trim root-cause fix (A-3) which resolves it as a side effect.

<!-- OPEN_QUESTIONS -->

- **Q-1**: Should Story 4.3-bis (the decimal-scale fix, still open) land *before* A-1 (the annex-format extension), or alongside it? Landing A-1 first would let Story 4.3-bis's own review use the extended annex to confirm no other `à_clarifier`/`sourcée` column has the same latent gap, rather than fixing the 5 known columns and re-discovering others later.
- **Q-2** (edge-case lens, §2.3): can real KAPE22 data have a nonzero `NombreDemiProduit` on an OF whose `CodeOpeRefroidissoir`/`RangOpeRefroidissoir` are empty? If so, `AC-FR20-2`'s ingot/furnace distribution control silently never runs for that Fichier (`Kape22ImportBundleMapper.cs:84-87` returns early when Refroidissoirs is inapplicable, with no independent check that the inapplicability itself is legitimate). - **Q-3** (adversarial lens, §2.3): can the same OF legitimately be resubmitted under a different `NumeroFichier` (e.g. a corrected P60 for an OF already committed)? The D22 anti-duplicate guard (`OkLogRowExists`) keys on `NumeroFichier + OF`, so it does not catch this case; unlike `Coulee` (explicitly designed to be shared/reused across Fichiers, with its own existence check), `OrdreFabrication`/`SectionCharge*`/`Consignes` have no analogous reuse check — an unconditional `Add`. If same-OF resubmission is a real scenario, it currently surfaces only as a generic SQL PK-violation `PersistenceError`, not a named business cause. If it can never happen (each OF gets exactly one P60 file, ever), this is a non-issue and needs no action — a business-rule question, not a code decision.
