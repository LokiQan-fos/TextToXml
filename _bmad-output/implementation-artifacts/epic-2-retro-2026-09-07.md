Contrairement à l'Épic 1 (bibliothèque pure), l'Épic 2 change le comportement runtime
(EF Core, transactions SQL Server). Flux exercés de bout en bout :

- `dotnet test TextToXml.sln --filter Category=Unit` → **337 passés, 0 échec, 0 ignoré** (~1,5 s).
- `dotnet test TextToXml.sln --filter Category=Integration` → **12 passés, 0 échec** (2 s) contre une
  instance SQL Server locale + `scripts/schema/` :
  - `PersistenceSmokeTests` : connexion fixture, application des 4 tables, round-trip `INSERT`/`SELECT`
    sur `L_D_KAPE22` sous `TransactionScope` (base propre après).
  - `TransactionalPersistenceTests` (régime commit réel + `ResetData()` / `TRUNCATE`) : insert atomique
    `L_D_KAPE22` + `L_D_LOG_COMMANDE`, `InsertedId` = identity, rollback vérifié sur échec, garde-fou
    anti-doublon (2ᵉ tentative voit la ligne `… — OK` **commitée** → 0 insert), ligne « REJETÉ » sur
    `MapResult.Success == false`.
- Sans instance SQL Server : les 12 `SkippableFact` s'**ignorent avec message** (pas d'échec) —
  contrat AR-12 vérifié.
- Le worker lui-même (`Program.cs` / boucle `BackgroundService`) **n'est pas** exercé — c'est le
  périmètre Épic 3. `StartupCompatibilityHostedService` est testé unitairement (`StartupWiringTests`),
  pas via un hôte réel.
