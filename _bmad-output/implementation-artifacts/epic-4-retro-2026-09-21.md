This is `Category=Unit` — unlike the already-deferred `Kape22ProductionDataParityTests` gap, a regression here (a dropped `if (bundle.SectionChargeChutage is not null)` branch, or a genuinely out-of-gabarit `ChutagePied`/`ChutageTete`/`LongueurMoyenne`/`H2Coulee` value) would not be caught by anything in the unattended CI suite — it would surface as the raw, undiagnosed SQL overflow B-5 exists to eliminate. ### 2.5 OF re-dispatch under a different `NumeroFichier` bypasses D22 for 9 of the 10 downstream tables, unlike `Coulee` — corroborated independently by two lenses

**Source:** edge-case-hunter and adversarial lenses independently found the same interaction, re-verified this session. `Kape22Persister.OkLogRowExists` (`Kape22Persister.cs:81,211-215`) keys the D22 anti-duplicate guard on `(NumeroFichier, OF)`, not `OF` alone. `Kape22Persister.cs:92-96`'s `couleeAlreadyExists` check gives `L_D_COULEE` alone a graceful existence/reuse path, motivated (per the code's own comment at line 89-91) by "several OF from the same cast" reusing one `IdCoulee` — but the same OF reappearing under a corrected `NumeroFichier` is architecturally the same shape of legitimate repeat, and none of the other 9 OF-keyed tables (`L_D_ORDRE_FABRICATION`, keyed on `OF` alone, plus the 7 `SectionCharge*` and `L_D_CONSIGNES`) get an equivalent guard — `context.OrdreFabricationRows.Add(bundle.OrdreFabrication!)` at `Kape22Persister.cs:150` and the `AddIfPresent`/`AddRange` calls at lines 156-163 are unconditional.

**This is a concrete, sourced elaboration of the second retro's own carried-forward open question Q-3** ("can the same OF legitimately be resubmitted under a different NumeroFichier? ... Still unaddressed"), not a new question — Q-3 asked whether this scenario is legitimate; this finding shows precisely what happens today if it occurs: a PK-violation `DbUpdateException` on `L_D_ORDRE_FABRICATION` (and any populated `SectionCharge*`/`Consignes` rows) falls through to the generic `PersistenceFailure` catch as an undiagnosed `PersistenceError`, instead of the business-readable `BusinessRuleViolation`/REJETÉ path the Coulee-existence and Consignes-collision checks were specifically built to provide for an analogous situation.

**Disposition:** not routed as a blind fix — this needs the same human answer Q-3 already asked for (is the resubmission scenario legitimate at all?). Carried forward as **Q-3**, now with concrete supporting evidence instead of only a hypothesis.

### 2.6 `Coulee` reuse is a bare existence check with no data comparison — a later Fichier's differing Coulee data is silently discarded

**Source:** edge-case-hunter lens, re-verified. `Kape22Persister.cs:92-96`: `couleeAlreadyExists` is a plain `Any()` existence probe; when true, `bundle.Coulee` (this Fichier's own freshly-mapped `CouleeMapper.Map` output) is never compared against the row already on file, never merges, never raises a warning — it is simply not added.

**Disposition:** needs a business decision (should a later, differing dispatch update, warn, or — today's behavior — silently discard?), not a code decision. New open question, **Q-5** below.

### 2.7 Consignes-collision check (A-5) uses ordinal, case-sensitive `CodeOperation` comparison; `L_D_CONSIGNES`'s real PK is on SQL Server's default case-insensitive collation

**Source:** adversarial lens, re-verified against the code (not against the live database — no reachable SQL Server this session, see Evidence inventory). `Kape22Persister.cs:126`: `GroupBy(row => (row.OF, row.CodeOperation, row.TypeConsigne, row.ConsigneGPAO))` uses the default (ordinal) string equality. AscoLSI's schema is provisioned externally (AD-5, no EF migrations); SQL Server's default collation (`SQL_Latin1_General_CP1_CI_AS` and similar) is case-insensitive unless a column is explicitly marked otherwise, which no script under `scripts/schema/` does for `L_D_CONSIGNES`.

**Disposition:** fix now — cheap and mechanical (match the in-memory pre-check's case sensitivity to the real PK's), no design decision required. Routed as **C-2** below. Flagged as the finding this retro is least able to fully confirm without live-database access (the collation itself was not queried this session) — noted honestly rather than asserted as certain.

### 2.8 No guard equivalent to B-5 exists for the ~45 length-bounded string columns across the 10 downstream tables

**Source:** adversarial lens, re-verified. `DownstreamColumnLengths.cs` documents that `AscoLsiDbContext` applies these bounds via EF Core's `HasMaxLength` — schema/migration metadata only, not a client-side validation that throws before `SaveChanges` (confirmed: no length-check exists anywhere in `Kape22Persister.cs`, read in full). Unlike `FindMagnitudeOverflow` (B-5), which gives an oversized *decimal* a diagnosed `BusinessRuleViolation`/REJETÉ message, an oversized *string* on any of these ~45 bounded columns would only surface as a raw SQL truncation `DbUpdateException`, caught generically as an undiagnosed `PersistenceError`.

**Disposition:** defer — this is a new guard requiring the same kind of design choice B-5 itself needed (its own spec had an explicit "Ask First" on where the check lives and what it sources). Routed as **C-4** below, candidate for a future hardening story in the same lineage as 4.9/4.10.

### 2.9 B-1/B-2/B-5's completeness/parity guards are each pinned to a separately hand-maintained 5-mapper-file list

**Source:** adversarial lens, re-verified. `tests/Kape22Importer.Tests/DownstreamColumnMagnitudesParityTests.cs:20-26` (`TableByMapperFile`) hardcodes exactly the same 5 mapper filenames `MappingAnnexSchema.cs`'s `MapperScaleCallSites` extraction targets — two separate hardcoded lists (plus a third, implicit one: `DownstreamColumnMagnitudes.MaxAbsoluteValues`' own key set, whose `TryGetValue` in `FindMagnitudeOverflow` simply returns `false`/continues for an unregistered column instead of failing loudly).

**Disposition:** defer — real, but the 5-file list is accurate today (verified: `grep -rl "DecimalScale.Apply" src/Kape22Importer/*.cs` returns exactly those 5 files) and deriving it generically is a design choice, not a one-line fix. Routed as **C-3** below.
